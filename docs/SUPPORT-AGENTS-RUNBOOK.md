# Агенты поддержки: настройка и работа

Подтверждённые владельцем настройки и результаты проверки подключений от
07.09.2026: [SUPPORT-AGENTS-PILOT.md](SUPPORT-AGENTS-PILOT.md).

## Что реализовано

Режим `shadow` анализирует сохранённые обращения и ответы операторов в фоне. Клиентская переписка продолжает работать через существующий Telegram/Bitrix relay. Агент сохраняет русский черновик ответа, категории, рекомендуемые команды, список диагностических проверок и отдельные отчёты по качеству. Режим `assist` дополнительно создаёт внутренние Telegram-задачи, напоминает о проверках и отправляет руководителю сводки. В обоих режимах ответы клиентам остаются черновиками.

Режим `off` установлен по умолчанию. В нём нет запросов к модели. После миграции сообщения и задания сохраняются независимо от режима, поэтому при включении `shadow` может обрабатываться накопленная очередь в пределах лимитов.

- Классификация: общие вопросы, KYC, карты, платежи, технические ошибки, безопасность, жалобы, прочее; несколько категорий на обращение.
- Деньги: обязательная проверка оператором. В коде агента нет инструментов движения средств, повторов финансовых операций и изменения аккаунта.
- База знаний: опубликованные статьи API Turkarta или один проверенный локальный JSON-экспорт. Поиск по тексту без платных embeddings; ответ содержит идентификаторы и версии использованных статей. В первой версии генерация по KB доступна только для общих вопросов.
- Провокации: отдельный признак попытки изменить инструкции. Для явно постороннего запроса предусмотрена русская реплика «Хитро 😏 Но кухонный модуль мне не установили». Реальная проблема в том же сообщении сохраняет приоритет.
- QA: шесть критериев, конкретные сообщения-доказательства, авторство, ограничения данных и обратная связь руководителя. Автоматические приветствия не оцениваются как работа человека.
- Telegram: клиентские сообщения и ответы операторов сохраняются в общем журнале; метаданные источника предотвращают повторные задания при повторном поступлении одного сообщения.
- Bitrix: пока нет проверенного идентификатора автора, отчёт явно указывает неизвестное авторство и не назначает оценку конкретному сотруднику.
- Внутренние задачи: основной/резервный ответственный, атомарное принятие, комментарии, срок следующей проверки и ограниченное число напоминаний. История хранится отдельно от клиентской переписки.
- Руководитель: предварительные критичные замечания в отдельной группе, ежедневная сводка, защищённый API с диалогами-доказательствами и история правок обратной связи в БД.

## Запуск

1. Перед запуском обновлённого приложения применить миграции командой `pnpm migrate` в нужной среде. Миграции до `0013_support_agent_operations.sql` включительно обязательны даже при `SUPPORT_AI_MODE=off`. Приложение проверяет наличие таблиц до регистрации webhook.
2. Настроить переменные из `.env.example`: `OPENAI_API_KEY`, отдельный `SUPPORT_AI_ADMIN_SECRET` длиной не менее 32 символов, источник базы знаний и `SUPPORT_AI_MODE=shadow`.
3. Источник KB выбрать один:
   - `SUPPORT_AI_KB_API=https://<api>/api/knowledge-base` — опубликованные статьи; только HTTPS, без перенаправлений. До 100 статей, обновление каждые 5 минут. Непустые slug обязательны для загрузки через API.
   - `SUPPORT_AI_KB_FILE=/absolute/path/export.json` — массив `{slug,title,content,updated_at?,is_published?}` в формате редактора Turkarta. Экспорт должен быть проверен владельцем: отсутствие `is_published` считается разрешением включить статью. Не подмешивать внутренние инструкции в публичный экспорт.
4. Выполнить `pnpm typecheck`, `pnpm test`, `pnpm build`; запустить обычный сервис. Воркер запускается вместе с ним и обрабатывает по одному заданию за раз на процесс.

Ключи не передавать в браузер или Telegram. Административный секрет отличается от webhook-секретов клиентского приложения. `store:false` отключает сохранение ответа в Responses API, но сам по себе не означает нулевое хранение данных провайдером.

## Просмотр результатов

Серверный запрос:

```http
GET /api/internal/support-ai/tickets/<ticket-uuid>
x-support-ai-secret: <отдельный внутренний секрет>
```

Возвращает до 30 последних заданий с состоянием, результатом и признаком `stale`. Черновик с `stale=true` нельзя использовать без повторной проверки: после него появились новые сообщения. Значение `automatic_send_allowed` всегда `false`. Сам черновик не подтверждает назначение или отправку: состояния внутренних задач и доставки доступны отдельно.

Оценка руководителя:

```http
POST /api/internal/support-ai/reviews/<job-uuid>/feedback
Content-Type: application/json
x-support-ai-secret: <отдельный внутренний секрет>

{"verdict":"rejected","comment_ru":"Оператор не видел статус платежа; это недостаток инструмента."}
```

Варианты `verdict`: `accepted`, `rejected`, `needs_revision`. Все изменения сохраняются в `support_agent_review_feedback_events`. Общий внутренний секрет идентифицирует роль API, а не отдельного руководителя. Персональная аутентификация — следующий этап.

## Внутренние Telegram-задачи

Для `assist` настроить `SUPPORT_AI_INTERNAL_CHAT_ID` и `SUPPORT_AI_OWNER_ROUTES`. Для QA-уведомлений дополнительно указать `SUPPORT_AI_QA_CHAT_ID`. Добавить существующего support-бота в эти группы. Конфигурация запрещает использовать клиентскую relay-группу или группу лидов; группа QA также должна отличаться от группы внутренних задач. Настраивающий сотрудник отвечает за закрытое членство в этих группах — отдельный ID не заменяет контроль участников.

Пример маршрутов (ID условные, заменить реальными):

```json
{
  "support": {"primary_tg": 111, "backup_tg": 222},
  "payments": {"primary_tg": 333, "backup_tg": 444},
  "kyc": {"primary_tg": 555, "backup_tg": 666},
  "engineering": {"primary_tg": 777, "backup_tg": 888}
}
```

`support` обязателен как резервный маршрут для ненастроенных команд. Поддерживаются также `cards`, `security`, `support_lead`. Адресаты берутся только из конфигурации, никогда из текста клиента или ответа модели. Денежная и техническая проблема может создать две отдельные задачи.

В `assist` любое реальное обращение получает внутреннюю задачу для проверки человеком, включая черновик ответа по KB. Неудачный анализ создаёт задачу в `support`. Устаревшие результаты и закрытые обращения не порождают новые задачи. Пока задача команды открыта, новые сообщения обновляют её контекст, не сбрасывая пропущенный срок.

Действия в группе задач:

```text
/ai_accept <ID задачи>
/ai_update <ID задачи> Проверены логи; ожидается ответ провайдера
/ai_wait <ID задачи> Ждём подтверждения операции от провайдера
/ai_done <ID задачи> Оператор проверил результат и ответил клиенту
```

Принять задачу можно и кнопкой «Принять». Принятие доступно основному или резервному ответственному: одновременное нажатие не назначает двух владельцев. Обновлять и завершать может только принявший сотрудник. Комментарий от 5 до 2000 символов обязателен для обновления, ожидания и завершения. Проверяется Telegram ID из authenticated update, а для кнопок — связь с сохранённым сообщением бота.

Команды не двигают деньги, не перезапускают операции, не меняют статус карты/KYC и не отправляют комментарий клиенту. Закрытие внутренней задачи не закрывает клиентское обращение. Если клиентское обращение закрыто через обычный процесс, оставшиеся внутренние задачи отменяются при следующем проходе планировщика.

По умолчанию задача должна быть принята за 10 минут (`SUPPORT_AI_ACK_MINUTES`), затем следующая внутренняя проверка — через 60 минут (`SUPPORT_AI_UPDATE_MINUTES`). Эти интервалы работают круглосуточно по истёкшему времени, не учитывают график смен и не являются обещанием клиенту. При просрочке уведомляются текущий и резервный ответственные. После трёх напоминаний (`SUPPORT_AI_MAX_REMINDERS`) задача остаётся с признаком внимания в API и сводке; бесконечная рассылка прекращается. Напоминание сохраняет исходный пропущенный срок. Явный комментарий оператора задаёт новый срок.

Получение задач, истории действий и проблем доставки:

```http
GET /api/internal/support-ai/operations?ticket_id=<ticket-uuid>
x-support-ai-secret: <отдельный внутренний секрет>
```

Без `ticket_id` возвращаются до 100 открытых задач. Ошибки/неопределённые доставки показываются общей очередью, максимум 100 последних.

## Качество и ежедневная сводка

Если указан `SUPPORT_AI_QA_CHAT_ID`, критичные замечания направляются только в эту группу и явно обозначаются как предварительные. Отклонённое руководителем или устаревшее замечание отменяется, если уведомление ещё находится в очереди. Уже доставленный текст автоматически не удаляется и не редактируется.

Ежедневная сводка формируется после `SUPPORT_AI_DIGEST_HOUR_UTC` (по умолчанию 04:00 UTC, 09:00 Алматы) за предыдущий календарный день UTC. При простое несколько дней отправляется только последняя такая сводка, без массовой рассылки пропущенных дат. На группу/дату создаётся одна запись в очереди.

В сводке: количество проверенных диалогов, кандидатов на критичные замечания, ожидающих проверки руководителя, отклонённых оценок, случаев неизвестного авторства, устаревших обзоров, текущих непринятых/просроченных задач, проблем доставки, ошибок анализа и оценка затрат. Учитывается последняя завершённая оценка каждого диалога за день, а не сумма повторных оценок. Критичные кандидаты исключают отклонённые оценки и обзоры, устаревшие на конец отчётного дня. Статусы задач показываются на момент формирования, отдельно от статистики QA за день. Это не персональный рейтинг.

Сводка и до 100 последних обзоров диалогов за выбранную дату:

```http
GET /api/internal/support-ai/quality/2026-09-05
x-support-ai-secret: <отдельный внутренний секрет>
```

Ответ содержит конкретные отчёты с `ticket_id`, `job_id`, доказательствами и текущим признаком `stale`. Это позволяет проверить вывод и сохранить обратную связь через существующий endpoint.

## Доставка внутренних уведомлений

Уведомления сохраняются в `support_agent_notifications` атомарно с созданием/обновлением задачи. После отправки сохраняется Telegram message ID. Изменённая конфигурация назначения, закрытая задача и устаревшая версия уведомления отменяют ожидающую отправку.

При явном Telegram 429 допускается до трёх попыток с учётом `retry_after`. При явном отказе запрос становится `failed`. При сетевой неопределённости или падении процесса во время отправки — `unknown`: автоматического повтора нет, чтобы не создавать дубликаты. Такие записи видны в API и сводке. Оператор может принять существующую задачу командой `/ai_accept`, если кнопка недоступна; ручное разрешение неопределённых доставок пока выполняется администратором после проверки Telegram.

## Стоимость и отказы

По умолчанию используется `gpt-5.4-nano` без reasoning. Можно выбрать `gpt-5-nano` с минимальным reasoning; реальную стоимость и задержку сравнивать на своей выборке. Ставки в `src/agents/openai.ts` взяты из официальной документации на 05.09.2026; при изменении цен их нужно обновить.

Лимиты по умолчанию: $1 в сутки, $20 в месяц и 12 вызовов на обращение в сутки. Границы периода — UTC. Резервирование в PostgreSQL сериализуется между процессами. После ответа учитываются input/output tokens, включая reasoning в составе output. При неизвестном исходе запроса резерв сохраняется. Кэшированные токены считаются по полной ставке: оценка консервативная. Это лимит вычисляемой здесь стоимости, а не замена лимиту расходов аккаунта провайдера.

Ошибки модели не повторяются бесконечно: задание получает `failed` и краткий код. Просроченная аренда воркера допускает одну повторную попытку; устаревший воркер не может перезаписать результат. Новые сообщения объединяются через отмену устаревших ожидающих заданий. При ошибке KB используются контролируемые ответы без выдуманных статей, а в отчёте ставится `kb_available=false`.

В журнале модели хранятся идентификаторы, стоимость и задержка. Код не логирует текст запросов, секреты или полный ответ провайдера. Маскирование email, очевидных карточных номеров и подписанных OTP — дополнительная мера, не полноценная система удаления всех персональных данных. Документы и изображения модель пока не читает.

## Проверка

`pnpm test` проверяет политику и интеграционные границы с подставным ответом модели. Это не измерение качества реальной модели и не доказательство абсолютной защиты от prompt injection.

Тест PostgreSQL дополнительно запускается с `SUPPORT_AI_TEST_SOCKET`, указывающим на специально созданный временный кластер `/private/tmp/turkarta-support-ai-*`, порт Unix socket 55437, база `postgres`. Тест применяет миграции и пишет только синтетические записи. Не подключать его к рабочей базе.

До включения автоматических ответов нужна размеченная выборка реальных обращений на русском: обычные вопросы, финансовые проблемы, CSB 500 с неизвестным исходом, смешанные провокации, ошибки классификации, неполные переписки и хорошие/плохие ответы людей. Оценить точность маршрутизации, долю необоснованных ответов, согласие QA с руководителем и p95 времени ответа.

## Следующие этапы

1. Подтвердить актуальную KB, ответственных и критерии QA; проверить live-вызовы модели в разрешённой среде.
2. Подключить достоверное авторство/назначение операторов Bitrix. Read-only адаптер внутренних статусов реализован; его нужно настроить на нужную среду Turkarta API. Прямой доступ к логам и проверка статусов у провайдеров пока отсутствуют.
3. Настроить реальные группы/ответственных и проверить внутренние Telegram-задачи и QA-сводки в тестовой среде. Добавить графики смен, приоритетные сроки и администраторский интерфейс для сбоев доставки.
4. Добавить интерфейс просмотра с персональной аутентификацией; API, ежедневные сводки и журнал обратной связи уже реализованы.
5. После оценки разрешить отправку утверждённых ответов в выбранных категориях с контролем передачи человеку и доставки.
6. Подключить подготовку проверенных исправлений в изолированной среде разработки. Развёртывание и любые финансовые действия не входят в полномочия этого агента.

Реализованы анализ в фоне, внутренние задачи/напоминания и QA-сводки с настраиваемой доставкой в Telegram. Автоматические клиентские ответы, проверка CSB в реальном времени, подготовка патчей, персональное авторство операторов Bitrix и веб-интерфейс ещё не реализованы. ## Внутренняя диагностика аккаунта

В Operations настроить `SUPPORT_AI_DIAGNOSTICS_URL` (HTTPS origin без пути) и
отдельный `SUPPORT_AI_DIAGNOSTICS_SECRET` минимум 32 символа. В новой версии
Turkarta API тот же ключ называется `SUPPORT_DIAGNOSTICS_SECRET`.
Endpoint — `POST /internal/support-diagnostics/snapshot`, заголовок
`X-Support-Diagnostics-Secret`. Старый API без этого endpoint даст безопасный
результат `unavailable`; отсутствие обеих настроек — `not_connected`.
Секреты webhook/admin/cron/провайдера для этой роли не использовать.

На обращениях о деньгах, картах, KYC и технических проблемах воркер читает
идентичность из записи обращения и запрашивает один ограниченный снимок.
До 20 карт, 10 последних операций, кэш KYC CSB и даты. Для Telegram с несколькими
связанными аккаунтами результат `identity_ambiguous`: данные не выдаются.
Номер карты, email и ID из текста клиента не используются для выбора аккаунта.

Полный снимок сохраняется в `results[].result.diagnostics` защищённого API
обращения. Краткое пояснение входит в задачу менеджера. Снимок не передаётся
модели и не создаёт дополнительных расходов на токены. Время HTTP ограничено
8 секундами, ответ — 64 КБ; неверная идентичность, неизвестные поля и снимок
старше 2 минут отклоняются. Возраст самого статуса определяется его собственной
датой: свежий HTTP-ответ не делает старую запись актуальной.

Это внутренние записи, а не новая проверка CSB. Операция из обращения не выбрана
автоматически. `funding_failed` и 5xx не доказывают отсутствие зачисления, наличие
предыдущей автоматической попытки требует отдельной сверки. Все действия с
деньгами остаются у оператора. Снимок не используется для ретроспективной оценки
ответов людей: сегодняшние сведения не доказывают, что оператор знал их вчера.

`GET /api/internal/support-ai/readiness` с `X-Support-AI-Secret` показывает режим,
модель, наличие настроек KB/диагностики/групп, список команд и лимиты расходов.
Значения ключей, адреса и Telegram ID не возвращаются. `connectivity=not_checked`
означает, что endpoint проверяет только конфигурацию: это не live smoke test.

Проверено локально 2026-09-06: 36 тестов Operations прошли, включая обе
PostgreSQL-интеграции; typecheck и build прошли. Проверены сохранение диагностики
в задаче, недоступность/неверная идентичность ответа и разделение секретов.
Реальные вызовы модели и доставка в Telegram для этого этапа не выполнялись.
